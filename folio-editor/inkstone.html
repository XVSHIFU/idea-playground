systemd 入门：你的 Linux 究竟如何启动

作者 季述 · 使用 墨纪 编辑

按下电源键，在你起身倒一杯水的工夫里，机器已经跑完了一场接力赛：固件自检、引导程序、内核，然后交接给用户空间的第一个进程——systemd。这篇教程拆解这场接力的最后一棒，读完你就能用一条 systemctl 和一个自己写的 unit 文件，管好属于自己的服务。

01从按下电源到看见登录框#

Linux 的启动过程并不神秘，本质是一场四棒接力：固件做完硬件自检，把控制权交给引导程序；引导程序把内核装进内存；内核初始化一切，最后在用户空间拉起 1 号进程。此后的一切——网络、登录提示符、图形界面——都由这位 1 号进程照看。

在绝大多数现代发行版上，这位 1 号进程就是 systemd。它是所有进程共同的祖先，也是我们今天的主角。

在终端里可以亲眼确认这一点：ps -p 1 会告诉你 PID 1 的名字。下面是一台普通机器上电后最初几秒的样子：

02Unit：最小积木#

在 systemd 的世界观里，万物皆 unit（单元）。一个服务是一个 unit，一个挂载点是一个 unit，连“系统就绪”这个状态本身，也是一个 unit。把大问题拆成小积木，再声明积木之间的关系——这是它管理复杂性的方式。

后缀类型典型用途
.service服务守护进程，例如 nginx、sshd
.target编组一组 unit 的“里程碑”，如 multi-user.target
.timer定时器计划任务，现代写法替代 crontab
.socket套接字按需启动：有连接进来才唤醒服务
.mount挂载点分区与文件系统的自动挂载

其中最常见的是 .service，接下来我们所有的操作都围绕它展开。

03systemctl：日常主力工具#

systemctl 是你与 systemd 对话的窗口。别被它几十个子命令吓到——日常真正高频的，只有下面这一小撮：

bash 
# 查看状态——信息量最大的一条命令
systemctl status nginx

# 启动 / 停止 / 重启，即时生效
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx

# 开机自启：enable 写入启动清单，--now 表示顺手立刻启动
sudo systemctl enable --now nginx

# 脚本里判断状态，取 exit code 更方便
systemctl is-active nginx # 活跃输出 active，退出码 0
start 与 enable 是新手最常混淆的一对。

start 是“现在就跑”，重启后不会自动恢复；enable 是“把名字写进开机清单”，要等下次启动才生效。两者互不替代，组合 --now 才是现代写法。

04写一个你自己的服务#

假设我们有一个小小的 API 程序，希望它随系统启动、崩溃后自动拉起。用任何语言写完之后，剩下的全部工作，只是写一份不到十行的声明式配置。

demo-api.service 
[Unit]
# 人类可读的描述，会出现在 status 输出里
Description=Demo API Service
# 排序：等网络就绪之后再启动（不构成强依赖）
After=network-online.target
Wants=network-online.target

[Service]
# 注意：路径必须写绝对路径
ExecStart=/opt/demo/api --port 8080
# 非正常退出时 3 秒后自动重启
Restart=on-failure
RestartSec=3

[Install]
# enable 时把它挂到 multi-user.target 下
WantedBy=multi-user.target

三个小节，各管一件事

  • [Unit] 管“我是谁、我等谁”。Description 给人看，After / Wants 声明先后顺序。
  • [Service] 管“怎么跑”。ExecStart 是唯一的必填项，Restart 是它比 nohup 优雅的全部理由。
  • [Install] 管“和谁绑定”。WantedBy=multi-user.target 等价于宣告“多用户模式就绪时带上我”。

写完之后，三步上线：

bash 
sudo cp demo-api.service /etc/systemd/system/
# 让 systemd 重新读取磁盘上的配置
sudo systemctl daemon-reload
sudo systemctl enable --now demo-api
改了 unit 文件却忘记 daemon-reload？

systemd 读的是内存里的旧配置，systemctl restart 也不会生效，日志里还会留一行警告。每次修改后先 daemon-reload，这是排第一位的坑。

05用 journalctl 读日志#

systemd 接管的另一件大事是日志。所有 unit 的输出统一进入二进制日志，带索引、可过滤、可追溯开机序号，从此不必再在 /var/log 里满地 grep。

bash 
# 跟踪某个服务的日志，类 tail -f
journalctl -u demo-api -f

# 只看最近一小时
journalctl -u demo-api --since "1 hour ago"

# 本次开机以来的所有错误级别日志
journalctl -p err -b
日志是程序的自白。journalctl 存在的意义，是让你一字一句地听见它。 —— 某位在凌晨排查故障的运维工程师

06进阶：target 与依赖图#

把多个 unit 编成 target，把 target 编成更大的 target，系统启动就是一张依次点亮的依赖图。想看清这张图，一行命令足矣。

展开进阶阅读：依赖图与默认 target 选读

multi-user.target 表示“多用户字符界面就绪”，graphical.target 在它之上再点亮图形登录。enable 一个服务时，systemd 实际只是在对应 target 的 wants 目录里放了一个软链接：

bash 
# 查看当前默认的启动里程碑
systemctl get-default
# multi-user.target

# 可视化依赖树，两页翻完你就懂了大半
systemctl list-dependencies multi-user.target

# enable 的真面目：一个软链接
ls -l /etc/systemd/system/multi-user.target.wants/

单用户救援也有对应的里程碑：rescue.target 与 emergency.target。在 GRUB 内核参数里追加 systemd.unit=rescue.target，就能进入一个几乎无服务的最小环境修系统。

07收束：一张最小清单#

  1. 万物皆 unit，服务只是最常见的 .service。
  2. 日常三板斧：status、start / stop / restart、enable --now。
  3. unit 文件三小节：[Unit] 定身份、[Service] 定行为、[Install] 定归属。
  4. 改配置必 daemon-reload，出问题先 journalctl -u。

每天都在用的三个 Bash 快捷操作

作者 季述 · 使用 墨纪 编辑

不追求技巧的堆砌，只记三条每天都会按到的小操作。每一条都省不了几秒钟，但每天都在省。

01花括号展开：一次建好一排目录#

bash 
mkdir -p logs/{nginx,redis,mysql}

# 改扩展名同理：a.txt → a.md
mv a.{txt,md}

02!!：补一个 sudo 再跑一遍#

敲了半天的长命令，回车后才发现忘了 sudo。不必按上箭头挪到行首，两条字符解决：

bash 
apt install tree    # Permission denied…
sudo !!              # !! 会展开为上一条命令

03Ctrl + R：向历史要回那条命令#

按住 Ctrl + R，输入一两个关键字，历史命令立刻浮出。没找对就继续按 Ctrl + R 往前翻，回车执行，按左右箭头可以停下来编辑。

一个小提醒。
