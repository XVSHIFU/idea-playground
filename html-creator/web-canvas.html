用 systemd 托管你的第一个服务

把一个随手启动的程序，变成开机自启、崩溃自愈、日志可查的系统服务。整个过程只需要一个二十行以内的文本文件。

舟舟子 2026 年 11 月 10 日更新 约 8 分钟读完 适用于 Debian 12、Ubuntu 24.04、Rocky 9
    回到顶部

    为什么不继续用 nohup

    很多人的第一个「后台服务」是这样诞生的：SSH 登录服务器，敲下 nohup python3 app.py &，然后合上电脑。它确实能跑，但你很快会遇到三个问题：机器重启后没人把它拉起来；进程崩溃了要等用户报障才知道；日志堆在一个越写越大的 nohup.out 里。

    systemd 是如今绝大多数发行版的 1 号进程，它本来就负责启动和看护系统里的一切。把你的程序交给它，上面三个问题会一次解决，而且不需要安装任何额外的软件。

    准备一个可以运行的程序

    为了把注意力放在 systemd 本身，这里用 Python 自带的静态文件服务器作为示例。先创建一个专用的系统用户和目录，服务不应该以 root 身份运行。

    终端bash
    # 创建不能登录的系统用户
$ sudo useradd --system --no-create-home --shell /usr/sbin/nologin notes

# 准备站点目录和一张首页
$ sudo mkdir -p /opt/notes/public
$ echo '<h1>It works</h1>' | sudo tee /opt/notes/public/index.html
$ sudo chown -R notes:notes /opt/notes

    在交给 systemd 之前，先手动运行一次，确认命令本身没有问题。看到监听提示后按 Ctrl + C 退出即可。

    编写 unit 文件

    systemd 把它管理的每一样东西称为一个 unit，服务对应的是以 .service 结尾的文本文件。新建 /etc/systemd/system/notes.service，写入下面的内容。

    /etc/systemd/system/notes.serviceini
    [Unit]
Description=Notes static site
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=notes
WorkingDirectory=/opt/notes
ExecStart=/usr/bin/python3 -m http.server 8080 --directory /opt/notes/public
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
    放在哪个目录

    自己写的 unit 一律放在 /etc/systemd/system。/usr/lib/systemd/system 属于软件包，升级时会被覆盖。两处同名时，前者优先。

    逐项看懂这些字段
    After / Wants
    等网络就绪后再启动。After 只管顺序，Wants 才会把依赖拉起来，两者通常成对出现。
    Type=simple
    ExecStart 启动的进程就是主进程，适合所有在前台运行的程序。
    ExecStart
    必须写可执行文件的绝对路径，这里不经过 shell，管道和重定向都不会生效。
    Restart
    on-failure 表示只在异常退出时重启，用 systemctl stop 正常停止不会触发。
    WantedBy
    决定 enable 之后挂到哪个启动目标上，多用户模式是服务器的常规选择。

    启动、自启与状态

    每次新增或修改 unit 文件，都要先让 systemd 重新读取配置，然后再启动服务。enable --now 会同时完成「设为开机自启」和「立即启动」两件事。

    终端bash
    $ sudo systemctl daemon-reload
$ sudo systemctl enable --now notes.service
$ systemctl status notes.service
● notes.service - Notes static site
     Loaded: loaded (/etc/systemd/system/notes.service; enabled)
     Active: active (running) since Tue 2026-11-10 09:41:07 CST; 4s ago
   Main PID: 2317 (python3)

    看到 active (running) 就成功了。服务在它的一生中会在几个状态之间流转，理解这张图，后面排错时就知道自己卡在哪一步。

    查看日志与排错

    程序写到标准输出和标准错误的内容，都会被 journald 收走并打上时间戳，不再需要自己管理日志文件。最常用的是下面两条命令。

    终端bash
    # 实时跟随日志，相当于 tail -f
$ journalctl -u notes.service -f

# 只看最近十分钟里警告及以上级别的记录
$ journalctl -u notes.service --since "10 min ago" -p warning

    如果服务起不来，systemctl status 输出的最后几行通常已经给出了原因。下面是新手最常遇到的三种情况。

    status=203/EXEC

    systemd 找不到或无法执行 ExecStart 指向的文件。检查路径是否为绝对路径、文件是否有执行权限，脚本第一行的解释器是否存在。

    status=217/USER

    User= 指定的用户不存在。回到第二节确认 useradd 已经执行，或者用 id notes 验证。

    Start request repeated too quickly

    服务在短时间内连续失败，systemd 暂停了重试。先根据日志修掉真正的错误，再执行 sudo systemctl reset-failed notes.service 清除计数后重新启动。

    改完记得重载

    修改 unit 文件后直接 restart 不会生效，systemd 仍在使用内存里的旧配置。先 daemon-reload，再 restart。

    收尾：给服务戴上镣铐

    服务能跑之后，再花两分钟限制它能碰到的范围。在 [Service] 段末尾追加几行，即使程序被攻破，攻击者拿到的也只是一个几乎什么都做不了的进程。

    追加到 [Service]ini
    NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true

    重载并重启后，运行 systemd-analyze security notes.service 可以看到一份逐项打分的报告，分数越低代表暴露面越小。到这里，你已经拥有了一个会自己起床、摔倒了会自己爬起来、还会写日记的服务。

    写于十一月的一个雨夜

    我至今记得第一次在终端里敲下 ls 的那个下午。屏幕上什么图标也没有，只有一个闪烁的光标，像是在耐心地等我开口。

    后来的十年里，工具越来越快。补全在我想清楚之前就给出了答案，脚本替我跑完了我曾经逐行敲过的命令。我很感激这些，却也时常怀念那个需要查手册的年代。

    等待是一种阅读

    编译内核要四十分钟的时候，人会去读配置项旁边的说明。现在一切只要四秒，我们便只读报错。速度省下来的时间，并没有自动变成理解。

    快让我们抵达，慢让我们知道自己到了哪里。

    留一条命令给自己

    所以我给自己定了一个小规矩：每周挑一条已经用了很多年的命令，完整地读一遍它的 man 手册。上周是 find，我才知道它的 -newer 已经在那里等了我十年。

    这不是怀旧，只是想在一切都被加速的日子里，保留一小块按自己步速走路的地方。
