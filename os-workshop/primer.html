操作系统到底是什么？

操作系统是一套管理硬件、给程序提供服务，并把程序相互隔开的基础软件。Windows、Linux 系统、macOS 都有这样的能力。没有它，普通应用就得自己处理硬盘读写、键盘输入、内存分配，还容易互相覆盖数据。

先抓住四个问题：谁来用 CPU？数据放哪里？怎么读写设备？谁有权做这些事？后面的进程、内存、文件、权限，都是在回答这些问题。

计算

CPU 轮流执行不同任务。

存放

内存放运行中的数据，磁盘保存长期数据。

沟通

程序通过统一接口读文件、收网络消息。

保护

程序不能随意修改别人的数据。

用一个网站请求贯穿全文

  1. 你启动 Web 服务：系统创建进程，即这个程序的一次运行。
  2. 请求来了：服务的线程获得 CPU，执行处理请求的代码。
  3. 需要查文件：服务请求内核读数据，没读好时可以等待，让其他线程使用 CPU。
  4. 计算结果：程序使用自己的虚拟地址访问内存，硬件和内核共同完成转换与保护。
  5. 写日志：数据可能先进入内存缓存，再写到存储设备。
  6. 服务退出：内核回收大部分资源，父进程领取退出结果。

电脑的零件，与 Linux 的位置

从 CPU、内存、磁盘开始，把容易混用的词分开。

L40L41

程序怎样变成机器能做的事？

程序最终要变成 CPU 能执行的指令。CPU 是处理器，负责加法、比较、跳转、读写内存等操作。Python 由解释器执行，C 通常先编译成机器代码；这些软件最后都要让 CPU 执行机器指令。

位（bit）只能表示 0 或 1；通常 8 位组成一个字节（byte）。内存地址可先理解为每个字节的编号。1 KiB 是 1024 字节，1 MiB 是 1024 KiB；厂商标的 1 GB 通常是十进制的十亿字节，不能与 GiB 混算。

各个部件负责什么？

部件白话作用例子
CPU 与核心真正执行指令；核心提供独立的执行能力。4 核能让多个执行流同时推进，但不是所有程序都快 4 倍。
寄存器、CPU 缓存寄存器是 CPU 眼前极小的工作格；缓存保存近期数据的副本。正在相加的数字进入寄存器；常用内存数据可能命中缓存。
内存 RAM运行时工作区，通常断电后内容消失。Python 列表、进程栈、文件缓存都可能占内存。
SSD 固态硬盘 / HDD 机械硬盘长期存放程序和文件，通常比内存访问慢。关机后文件还在，没有保存的编辑内容可能不在。
网卡等 I/O 设备与外界交换数据；I/O 就是输入/输出。网卡收数据包，键盘发输入，磁盘返回文件内容。

例如打开照片：照片原来在 SSD 上；系统把所需数据读进内存；CPU 执行解码程序；显示设备显示图像。“磁盘还有 500 GB”不代表“程序还有很多内存”。

Linux、发行版、终端、Shell

内核是操作系统中直接管理核心资源的部分。严格说 Linux 是内核；日常“Linux 系统”往往指内核加命令、库、服务和包管理器组成的发行版，如 Debian、Ubuntu、Fedora。

终端是输入输出的窗口；Shell是解释命令的程序，例如 Bash。输入 ls，Shell 找到并启动它，ls 再通过系统接口读取目录。Shell 是普通用户空间程序，不是内核。

“用户空间”是普通应用活动的范围；“内核空间”是内核运行、管理系统的范围。下一节解释为什么要分开。

服务器与普通电脑

两者遵循相同计算原理。服务器更关注长期运行、远程维护、扩展与故障处理，可能配备纠错内存（ECC）、冗余电源、远程管理控制器和热插拔磁盘；不是所有服务器都有全部这些功能。

双电源能在一只电源故障时继续供电，但应用写错文件仍可能丢数据。硬件冗余、备份、程序正确性分别解决不同问题。

被问装机经验时，可以解释主板连接 CPU、内存、存储、网卡，电源供电，散热维持工作温度；没有实际经历就说明掌握原理，不编造做过的操作。

停一下，试着解释：增加硬盘容量，为什么不一定解决程序内存不足？

磁盘与 RAM 是不同资源。交换空间可以暂存一部分内存页，但访问更慢，也不能无限承接工作负载。

学完后，你可以这样说

CPU 执行指令，内存提供运行时工作区，磁盘保存长期数据。Linux 内核管理这些资源，发行版再加入命令和服务。Shell 解释命令，它本身也运行在操作系统之上。

程序怎样请内核帮忙

系统调用、用户态、内核态、中断与异常。

L08L09

为什么不能让所有程序直接控制硬件？

因为一个程序的错误，不应轻易破坏整台机器。如果任何程序都能改任意内存、直接控制磁盘，一次越界写入就可能毁掉其他程序或系统。

处理器提供不同执行权限。简化地说，用户态运行普通应用，受硬件限制；内核态允许运行管理机器所需的特权操作。这是 CPU 的执行权限，不是登录账号权限：root（Linux 超级用户）启动的普通程序仍主要在用户态运行。

系统调用：进入内核的受控入口

系统调用是程序向内核请求服务的接口，例如打开文件、读数据、创建进程。程序通过规定入口交出请求号和参数，内核检查后处理。

  1. 程序调用 read(fd, buffer, n) 一类接口。fd 是打开对象的编号，第 08 节讲；buffer 是接收数据的缓冲区，也就是一块暂存数据的内存；n 是最多希望读取的字节数。
  2. 库封装准备参数，CPU 经系统调用入口进入内核。
  3. 内核检查对象和权限，寻找数据。如果必须等设备，当前线程可能阻塞。
  4. 数据准备好，线程得到运行机会，内核返回结果，继续用户态代码。

一次系统调用不一定发生线程切换。如果马上处理完，仍可由同一线程继续执行。进入内核与把 CPU 换给其他线程，是两个动作。

中断与异常：另外两类进入内核的原因

情况原因例子
中断外部设备或计时器需要 CPU 处理，通常不是当前指令直接引起。网卡通知数据到达；计时器提醒检查调度。
异常执行当前指令时发生需要处理的情况，与这次执行相关。访问的内存页暂未映射，触发缺页异常。
系统调用程序主动、受控地请求内核服务。读文件、创建进程；具体入口依架构而异。

通常要保存必要现场，运行处理逻辑，再返回合适位置，必要时进行调度。异常不等于一定崩溃：缺页有时只需建立映射或调入数据；非法访问才可能收到信号并终止。术语分类和优先级依处理器架构，不背“所有中断永远比所有异常优先”。

停一下，试着解释：调用一次 read，就一定切换到另一个进程吗？

不一定。read 通常涉及进入内核，但数据就绪时可直接返回；需要等待、被抢占等情况才可能换执行线程。

学完后，你可以这样说

用户态与内核态提供执行权限隔离。应用通过系统调用请求服务，设备通过中断通知，执行指令遇到特定情况会触发异常。进入内核不等于一定发生进程或线程切换。

进程：程序的一次运行

从启动到退出，理解状态、父子关系与僵尸。

L05L06

文件不动，进程在运行

进程是程序运行时的一整套环境和状态。包括地址空间、打开的文件、身份信息和至少一个执行线程等。同一份程序可以启动多次，各有对应进程。

PID 是进程编号；PPID 是父进程编号。你在终端运行两个 Python 程序，虽使用同一个解释器文件，通常拥有不同 PID，也有各自的内存数据。

Shell 怎样启动外部程序？

常见模型是 fork → exec → wait。实际 Shell 可能用其他创建机制优化，也有不需要启动新进程的内建命令。

  1. fork 创建子进程。子进程从 fork 返回处继续，但返回值与父进程不同，可以走不同分支。
  2. exec 用指定程序替换当前进程的程序映像。“替换”不是再创建新 PID。
  3. wait / waitpid 让父进程领取子进程退出状态，并回收相应记录。前台命令时，Shell 通常等它结束再给提示符。

fork 后不是“两个进程随便共用所有变量”。Linux 常用写时复制优化，第 07 节再解释。

五状态：谁在执行，谁在等待？

状态意思怎样离开
新建正在建立运行结构。准备好后进入就绪。
就绪条件已满足，只差 CPU。调度器选中后运行。
运行此刻在 CPU 上执行。用完时间片回就绪；等事件转阻塞；完成后终止。
阻塞 / 等待缺少某个条件，给 CPU 也做不下去。事件完成后回就绪，再等待调度。
终止执行结束，进入资源清理阶段。退出状态由父进程等领取。

请求磁盘数据：运行 → 阻塞；磁盘完成：阻塞 → 就绪；调度到它：就绪 → 运行。在这个教学模型中，不应把“磁盘完成”画成“立即运行”。

Linux 的 ps 字母不是五状态逐字翻译。R 同时包括运行与可运行；S 常为可中断睡眠；D 是不可中断睡眠；T 是停止；Z 是僵尸。D 常与 I/O 等待有关，但不只意味着本地磁盘坏了。

僵尸与孤儿，谁“死了”？

僵尸已结束执行，但父进程还没领取退出记录。它不再执行普通代码，但保留少量内核记录。发更强的终止信号不能代替回收。

孤儿是父进程先退出，自己还在运行。Linux 把它交给适当的收养者，可能是子进程收割器（subreaper），否则交给相应 PID 命名空间的 init，不能一律说“总由宿主机 PID 1 直接收养”。

子任务先完成、父程序忘了 wait，可能留下僵尸；父程序先退出、长任务还在跑，就出现孤儿。重点检查父程序的生命周期管理。

小实验：fork 与回收

python
import os

pid = os.fork()  # Unix 类系统；Windows 原生 Python 没有此接口
if pid == 0:
    print("子进程：fork 返回 0", flush=True)
    os._exit(0)
else:
    child_pid, status = os.waitpid(pid, 0)
    assert child_pid == pid and os.WIFEXITED(status)
    print("父进程：已回收子进程，退出码", os.WEXITSTATUS(status))

父进程拿到子 PID，子进程拿到 0。waitpid(pid, 0) 等待指定子进程。预期先子后父两行，退出码 0，不会故意留下僵尸。使用独立、单线程脚本运行，不嵌入已有多线程服务。

本次已在 Linux / Python 3 实际执行：先输出子进程信息，再回收并输出退出码 0。

停一下，试着解释：exec 成功后，会回到原程序下一行吗？

不会。成功的 exec 已替换程序映像；调用失败时才返回错误，原程序可以处理失败。

进程是程序的一次运行，拥有资源环境。fork 创建子进程，exec 加载另一程序，父进程用 wait 领取退出状态。僵尸是已退出未回收，孤儿是父进程先退出。

线程、协程与 CPU 调度

一个 CPU 为什么看起来能同时做很多事？

L01L02L03L04

进程像一间工作室，线程是里面的工作者

线程是执行代码的一条路线。同一进程的线程通常共享地址空间和打开的文件，但各自有寄存器现场和栈。栈记录函数调用过程中的返回位置、局部数据等。进程侧重资源环境，线程侧重执行。

例如一个服务器进程开四个线程处理请求，它们可以读同一份共享配置，却不能不加控制地同时修改同一计数器。共享带来方便，也带来下一节的并发问题。

线程间并非完全隔离：它们的栈虽然分别使用，但在同一地址空间中，并不具有进程之间那样的硬件隔离。一个线程越界写，可能伤到别的线程。

并发与并行，差一个字

并发是多个任务在同一段时间内交错推进；并行是它们在同一时刻实际执行。一个执行核心轮流处理 A、B，也能并发；让 A、B 真正同时执行，通常需要多个可用的硬件执行单元。

你一边等待下载，一边打字，就是不同工作共同推进。等待网络的任务不必占住 CPU。线程也不是越多越快：任务之间抢锁、CPU 切换、缓存失效都可能拖慢它。

调度器怎样“轮流安排”？

调度器是内核中决定下一步运行哪个可运行任务的机制。为了教学，先看时间片轮转：每个任务最多连续运行一小段，用不完工作就排到队尾。

换任务前必须保存“刚执行到哪里、寄存器是什么”，再恢复另一任务的现场，这就是上下文切换。可能由时间片/抢占、等待 I/O、等待锁、主动让出执行等引起。切换不同进程还可能涉及地址空间变化；同进程线程一般不用换进程地址空间，但仍有调度与缓存成本。

模型：A 需 5 个时间单位，B 需 3 个，C 需 1 个，都在时刻 0 就绪。时间片 2 时，顺序是 A、A、B、B、C、A、A、B、A，总计算时间 9。这里忽略切换耗时。

亲手给 CPU 分时间片

单核、任务同时到达、没有 I/O、忽略切换成本。展示时间片轮转，不代表现代 Linux 所有调度策略。

如何读演示里的指标？

响应时间＝第一次得到 CPU 的时刻 − 到达时刻；周转时间＝完成时刻 − 到达时刻。在本模型中，等待时间＝周转时间 − 实际计算时间，因为没有其他阻塞。

时间片 2：C 在时刻 4 第一次执行，5 时完成，所以响应 4、周转 5、等待 4。时间片变小可能更快照顾短任务，但现实中切换更频繁也会消耗时间。不能简单说“越小越好”。

协程与 Go 的 G / M / P

协程是由语言运行时或库管理的执行任务，可以暂停并在以后继续。多个协程可复用较少的操作系统线程。适合大量等待，不会凭空增加 CPU 算力。

例如几千个请求多数在等网络，不必每个请求都永久占用一个线程。运行时把能推进的协程交给线程执行；但某些阻塞调用仍可能阻塞承载线程。协程切换通常较轻，不保证所有实现、所有负载下都比线程快。

Go 中：G 是 goroutine 任务；M 是操作系统线程；P 是执行 Go 代码所需的运行时调度资源。P 不是物理 CPU，M 也不必与 P 数量相等。GOMAXPROCS 控制同时执行 Go 代码的并行额度，不能当“线程总数”。默认值涉及 Go 版本、CPU 可用性及容器限制；例如 Go 1.25 引入了容器感知默认行为。

此外，“OS 支持线程并行”不代表任何语言代码都能直接利用它。具体语言运行时也可能加限制。先掌握 OS 模型，再讨论语言实现。

停一下，试着解释：4 核机器开 100 个线程，能同时跑 100 份纯计算吗？

不能因此得到 100 份独立 CPU 算力。运行数量受可用硬件执行能力、CPU 配额、亲和性和程序同步等限制。多数可运行线程仍须排队。

学完后，你可以这样说

进程提供资源环境，线程执行代码，协程通常由用户态运行时调度。并发是交错推进，并行是同时执行。调度器安排 CPU，上下文切换保存和恢复现场，所以线程和协程都不是越多越快。

同时做事，为什么会出错？

竞态、锁、同步、死锁与进程通信。

L07

两个“加一”，怎么只加了一？

共享数据的操作如果交错执行，结果可能取决于执行顺序。例如计数器从 0 开始，A、B 都做“加一”。这个动作在教学模型中分为读取、计算、写回，不是一个不可分割动作。

  1. A 读到 0，准备写 1。
  2. B 也读到 0，准备写 1。
  3. A 写回 1。
  4. B 再写回 1。结果为 1，而不是 2。

这叫竞态条件：结果受时序影响。真正处理器、编译器和语言内存模型更复杂；这里先抓住“读—改—写被打断”的问题。不能靠一次运行没出错证明代码安全。

动手观察 · 教学模型

亲手制造一次丢失更新

每个任务只执行一次“读取旧值，再写旧值 + 1”。这是可控交错模型，不依赖真实线程碰运气。

锁与同步，解决什么问题？

临界区是访问共享资源、需要控制并发的那段代码。互斥锁让同一时刻最多一个执行者进入指定临界区。必须把整个“读—改—写”都保护起来，只锁住最后写回仍可能出错。

原子操作把特定操作表现为不可被其他执行者观察到中间状态的一步，但多步业务规则不一定能用一个原子加法解决。同步还包括“必须等某个条件满足才继续”，不仅是互斥。

条件变量允许线程在条件未满足时释放关联锁并等待，被唤醒后重新持锁检查条件，通常写在循环里。信号量是可消耗、可归还的计数，用来控制同时访问的数量，例如最多 3 个任务使用某资源。

例子：生产者把任务放进队列，消费者等待“队列非空”。队列的修改要互斥，“有新任务”要唤醒等待者。不要拿着锁不停死循环等生产者，否则生产者也进不来。

死锁：每个人都等别人先放手

死锁是多个任务互相等待，使它们都不能继续。A 拿着锁 X 等 Y，B 拿着 Y 等 X，就形成环。

必要条件白话解释
互斥资源不能同时给多个请求者使用。
占有并等待拿着已有资源，再等其他资源。
不可剥夺不能强行抢走已分配资源；通常由持有者主动释放。
循环等待A 等 B，B 又经某条链等回 A。

四个条件同时具备才可能发生这类资源死锁，不能说“看到互斥就发生死锁”。常用做法是统一加锁顺序：大家先 X 后 Y，破坏循环等待。也可以一次申请全部所需资源，或使用超时、回退与重试；超时只提供处理机会，不自动保证业务正确。

饥饿是某个任务长期拿不到机会；活锁是大家不断改变行为却没有实际进展。它们与“都卡住不动”的死锁不同。

进程隔离了，怎么交流？

IPC 就是进程间通信。管道像一条传字节的通道，常用来连接父子进程或 Shell 命令；消息队列按消息交流；共享内存让双方映射同一块数据，但仍需自己同步；socket 是通信端点，既能本机通信，也能走网络；信号主要用于通知事件，例如请求终止。

例如 printf 'a\nb\n' | wc -l 中，前一个命令的输出通过管道交给后一个命令。它们不需要共享 Python 变量，也能完成协作。

停一下，试着解释：每次写计数器时都加锁，读取却在锁外，够吗？

对于这里的读—改—写，不够。两个任务仍可能读到同一个旧值。必须保护整个逻辑，或用适当原子操作完成同等语义。

学完后，你可以这样说

并发访问共享数据时要控制临界区，否则可能丢失更新。互斥解决同时进入，同步还解决先后条件。死锁需要四个必要条件，统一资源申请顺序是常见的预防办法。

LESSON 06建议边读边练 · 约 25 分钟

内存：程序看到的地址是真的吗？

地址空间、分页、页表、TLB 与缺页。

L22

先看程序需要存什么

内存保存正在使用的指令与数据。一个进程的地址空间中通常有代码、全局数据、堆、栈及各种映射区域。堆是动态申请内存常用的区域；栈与函数调用密切相关。语言运行时可能在这些区域之上再做自己的管理。

例如程序读入 100 万条日志，保存字符串的对象可能不断占用动态内存。删除变量名不一定立刻把内存交还操作系统，中间可能有垃圾回收器与内存分配器。

为什么不直接把真实 RAM 地址给程序？

虚拟内存让每个进程看到自己的地址空间，再把地址映射到实际存储。这样更方便隔离、共享、按需分配和安排内存。它不等于“把硬盘当内存”，即使不启用交换空间，也仍然使用虚拟内存。

进程 A 的地址 0x1000 与进程 B 的 0x1000，可能对应不同物理内存；也可能通过受控共享映射指向同一物理页。只比较两个进程里打印的地址，不能判断是否用了同一块 RAM。

分页：把大空间切成小块

页是虚拟地址空间的一块；页框是物理内存中对应大小的一块。这里假设页大小为 4 KiB＝4096 字节。实际页大小依架构和配置，也可能使用大页。

页表记录虚拟页对应哪个物理页框、是否存在、是否可写等。CPU 内的MMU（内存管理单元）根据这些信息做地址转换和权限检查；内核负责建立、更新映射。TLB是地址转换结果的高速缓存，减少反复查页表的成本。

计算例子：虚拟地址 4200，除以 4096，商为 1、余数为 104，所以在虚拟页 1 内偏移 104 字节。若页 1 映射到物理页框 2，物理地址就是 2 × 4096 + 104 = 8296。页号变了，页内偏移没变。

动手观察 · 教学模型

把一个虚拟地址翻译成物理地址

模型只有 4 个虚拟页，合法地址为 0–16383。页 2 起初尚未驻留，但属于合法区域。真实系统还有多级页表等机制。

缺页不一定是错误

缺页异常表示这次访问不能直接用当前页表完成，需要内核处理。原因可能是尚未分配实体页、数据要从文件或交换区调入，也可能是写时复制或非法访问。

如果访问合法，内核可能分配、加载或复制页面，再让指令重试；如果地址根本不允许访问，就不能“补一页了事”，可能向进程发送 SIGSEGV 等信号。

TLB 未命中也不等于缺页。如果页表中已有有效映射，只需进行页表查找并更新转换缓存，不必读取磁盘。缺页也不一定访问磁盘，例如首次申请到一页清零内存。

停一下，试着解释：虚拟地址 8193 在第几页？页内偏移多少？

8193＝2 × 4096＋1，所以是从 0 编号的虚拟页 2，偏移 1。如果该页尚未建立有效映射，不能直接计算出可访问的物理地址。

学完后，你可以这样说

虚拟内存给进程独立地址空间，通过页表映射到物理页框。MMU 做转换和保护，TLB 缓存转换结果。缺页由内核处理，不一定代表非法访问，更不一定需要读磁盘。

LESSON 07建议边读边练 · 约 20 分钟

内存紧张时，系统会怎么办？

写时复制、缓存回收、交换空间与 OOM。

L23

fork 时把所有内存复制一遍，太贵了

写时复制（Copy-on-Write，COW）是先共享可共享的数据页，真正写入时再按需复制。普通 fork 后，父子进程的私有内存在逻辑上相互独立；Linux 通常先让它们指向相同物理页，并设置相应保护。

  1. 父进程变量值是 7，fork 创建子进程。
  2. 父子各自有地址空间，但暂时可读取同一个底层物理页。
  3. 子进程尝试写 9，触发写保护相关的缺页处理。
  4. 如果该页仍被共享，内核为写入方准备独立页、复制旧内容，再让写操作继续。父进程仍读到 7，子进程读到 9。

如果页面已无需共享，内核有时可直接恢复可写而不用再复制。COW 通常以页为单位；修改一个字节也可能触发整页复制。显式共享内存具有不同语义，不套用“永远相互独立”。

动手观察 · 教学模型

父子进程：先共享，写了再分开

只展示一个仍被父子共享的私有页。父子地址空间独立，底层物理页在写前暂时共享。

free 小，不一定是真的没内存

Linux 会把暂时不用的 RAM 拿来做文件等缓存。缓存保存可以再次获得的数据，避免反复读慢设备；其中一部分可在需要时回收。所以看到 free 很小，不能立刻判定“内存泄漏”。

free -h 的 available 是系统估算的不发生交换也可供新应用使用的内存，比只看 free 更有参考价值，但也只是估算。容器还可能有独立内存上限，宿主机有空闲不代表容器还能分配。

RSS 表示进程驻留在 RAM 的内存规模，可能包含共享页；直接相加多个进程的 RSS 会重复计算共享部分。VIRT / VSZ 是虚拟地址空间规模，不等于实际占用 RAM。

Swap 与 OOM

Swap（交换空间）可以把部分暂时不活跃的匿名内存页移到存储上，需要时再调回。匿名页指没有普通文件作为后备的数据页，例如很多堆内存。干净的文件缓存则常可直接丢弃，以后从文件重读，不一定要写入 swap。

如果活跃工作集超过可用内存，系统可能反复换入换出，忙于搬数据而不是做业务，这叫抖动。所以“加 swap”不等于获得同等速度的 RAM。

OOM 是内存不足场景。分配无法满足时，可能触发 OOM 处理并选择进程终止；也可能在某个资源限制下先失败。不是“free 变成 0 的瞬间一定杀最大进程”。选择与约束、内核行为、配置相关。

把概念用于排查

例子：服务最近变慢，vmstat 1 连续出现明显的 si/so（交换入/出），可用内存也低，怀疑内存压力导致换页。但“swap 用了 1 GB”单独一项不能证明此刻在频繁交换，要看持续活动和业务延迟。

如果某进程内存长期增长，继续检查对象是否释放、缓存是否有上限、请求量是否增长。内存泄漏指不再需要的内存仍无法释放；合理缓存增长与泄漏的处理方式不同。

停一下，试着解释：fork 后子进程把变量改为 9，父进程通常也变成 9 吗？

普通私有内存不会。写时复制只是物理实现优化，并没有取消父子进程在逻辑上的私有内存隔离。显式共享映射另当别论。

学完后，你可以这样说

COW 让 fork 后的私有页先共享，在写入时按需分开。内存紧张时系统可回收缓存、使用交换等；可用内存、换页活动与资源限制要一起看，不能只凭 free 或 swap 已用量判断。

文件：名字、内容与打开的编号

inode、文件描述符、链接与“删了还占空间”。

L10L11L12L19L25

一个文件，不只是一个文件名

文件系统把存储空间组织成文件和目录，并维护名字、位置和属性之间的关系。在常见 Linux 文件系统中，inode 记录文件类型、权限、大小、数据位置等元信息；目录里的目录项把文件名关联到 inode。

可以这样记：名字是目录里的标签，inode 是对象的资料卡，数据块是内容。实际实现可能有内联数据、扩展属性等细节，这个模型先帮助你分清“名字”与“对象”。inode 编号通常只在同一个文件系统内唯一。

路径是一串逐级查找的目录名，例如 /var/log/app.log。内核从根目录逐级找，过程中还要检查目录访问权限。路径不是直接的“硬盘地址”。

文件描述符：打开之后拿到的号码

文件描述符（fd）是进程用于引用打开对象的非负整数。通常 0、1、2 分别是标准输入、标准输出、标准错误。打开文件可能得到 3；另一个进程的 3 可以指向完全不同的对象。

更准确地说：进程的 fd 表引用内核中的打开文件描述，后者维护偏移、打开状态等，再关联实际对象。dup 或 fork 继承的描述符可能共享同一个打开文件描述，因此也可能共享偏移。

socket 是通信端点。在 Linux 上，它同样通过 fd 使用，但不是磁盘上的普通文件。管道、设备也可以有 fd，所以“文件描述符”不只服务磁盘文件。

句柄泄漏常指反复打开文件或连接却不关闭，导致 fd 数越来越多，最终触及限制。应检查打开/关闭是否配对，而不只是把上限调大。

硬链接与软链接

类型关联方式目标原名字被删除后
硬链接另一个目录项指向同一个文件对象，链接计数增加。通常不能跨文件系统，不允许普通用户给目录创建硬链接。只要还有其他硬链接，文件仍能按那个名字访问。
软链接 / 符号链接一个特殊文件保存另一条路径，可跨文件系统，也可指向目录。如果保存的路径已不存在，就成为悬空链接；不会自动追踪“原对象”的新名字。

例子：a.log 和 b.log 是硬链接，删 a 后仍可读 b；若 shortcut 是指向 a 的软链接，删 a 后 shortcut 可能失效，即使同一文件对象还能从 b 访问。

动手观察 · 教学模型

删的是名字，打开者还可能握着文件

初始有两个硬链接、一个打开引用。简化为普通本地文件，不涉及快照、映射或其他引用。只有所有名字和打开引用都消失，才满足模型中的回收条件。

为什么 rm 之后 df 仍然很满？

常见原因是：最后一个文件名已删，但进程仍持有打开引用。rm 删除名字并不等于让所有进程立刻关闭 fd。此时目录扫描工具可能已找不到它，而文件系统仍在为它占用空间。

df -h 看文件系统空间，du 沿目录统计文件；两者口径不同，本来就不保证完全相等。删除后仍被打开只是差异原因之一，还有快照、预留空间、挂载点遮蔽等情况。

排查可查看 lsof +L1 中链接数小于 1 的打开文件，再确认所属进程和日志重开机制。不要未确认影响就强杀服务。关闭或按应用支持的方式重新打开文件，才能释放相关引用。

import os
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as d:
    a, b = Path(d) / "a.log", Path(d) / "b.log"
    a.write_bytes(b"hello")
    os.link(a, b)
    fd = os.open(a, os.O_RDONLY)
    try:
        print("硬链接数：", os.fstat(fd).st_nlink)
        a.unlink()
        b.unlink()
        print("删除名字后，链接数：", os.fstat(fd).st_nlink)
        print("仍可通过 fd 读取：", os.read(fd, 5).decode())
    finally:
        os.close(fd)

权限：谁可以读、写、进入？

读懂 rwx、八进制、chmod 和 umask。

L13L14

三组人，三种基本权限

权限决定谁可以对文件或目录做什么。常见基本权限分三组：所有者 u、所属组 g、其他人 o。每组有 r（读）、w（写）、x（执行/搜索）。

rwxr-x--- 拆成 rwx | r-x | ---：所有者可读写执行；组成员可读执行；其他人没有这些权限。实际访问还要考虑目录权限、ACL、安全模块、挂载选项等，不能只看目标文件这一行。

目录的 x，不是“运行目录”

权限普通文件目录
r读取内容。读取目录项列表，即查看有哪些名字。
w修改文件内容。修改目录项，例如创建、删除、重命名；通常还需要 x。
x允许作为程序执行，还需格式、解释器等条件满足。搜索/穿过目录，按名字访问其中对象。

因此，删除文件主要取决于父目录的写入与搜索权限，不能只看文件是否可写。/tmp 常见的 sticky bit（粘滞位）还限制谁能删除或重命名里面的对象，防止共享目录用户随意删除别人文件。

为什么权限会写成 755？

每组用三个二进制位表示：r 的权值是 4，w 是 2，x 是 1，合起来形成一个八进制数字。7=4+2+1 是 rwx，5=4+1 是 r-x，6=4+2 是 rw-。

chmod 750 file 设置三组基本位为 rwx、r-x、---。chmod a-x file 表示从所有人权限中清除执行位；777 清除三个执行位得到 666，不是减一个十进制数 1。

chmod u+x 只加所有者执行位，a+x 给三组都加。省略 u/g/o/a 的 chmod +x 受 umask 影响，不总等于 a+x。数值模式还存在特殊位规则，此处练习限定普通文件的基本九位。

umask 是“禁止位”，不是默认权限

umask 是新建对象时用来清除权限位的掩码。在没有默认 ACL 改变规则的常见情形下：结果 = 程序申请的权限 & ~umask。这里 & 表示按位与，~ 表示按位取反；只讨论低九位。

普通文件常申请 666，目录常申请 777。umask 为 022 时，清除组和其他人的写位，普通文件得到 644，目录得到 755。普通文件本来没有执行位，不会凭空“减出来”。

反例：666 遇到 033，结果仍是 644，因为掩码中的执行位在 666 里本就没有。若用普通八进制减法，666−033＝633，就错了。程序也可以申请比 666 更小的权限；默认 ACL 存在时需按其规则判断。

I/O：等待数据时，CPU 在做什么？

缓冲、回写、阻塞、事件通知与 epoll。

L24L26

快的 CPU，为什么要等慢的设备？

I/O 是程序与设备或通信对象之间交换数据。CPU 很快，但磁盘、网络与其他参与者不一定立刻准备好。线程等待 I/O 时，内核可以让其他就绪线程运行，而不必让 CPU 空等。

阻塞调用在条件未满足时可能让当前线程睡眠等待；非阻塞调用不等条件完成，暂时不能进行就返回，例如 socket 读取返回 EAGAIN，表示现在没数据可读。非阻塞不代表“数据已经读取完成”。

异步 I/O则是提交请求后，稍后再获取完成结果。要区分“通知可以尝试读”与“通知读取已完成”：就绪通知不等于完成通知。

write 返回后，文件一定到硬盘了吗？

缓冲 I/O常通过内核的页缓存读写文件。读命中缓存可减少设备访问；写入先修改缓存页，形成脏页，表示它与持久存储内容还不一致。之后的回写再把数据送往存储。

因此普通 write 成功不等于断电后一定保留。应用自己的输出缓冲、内核缓存、设备缓存属于不同层。应用层 flush 常只保证把应用缓冲交下去，不能笼统等同于持久化。

fsync 用于请求同步文件数据及必要元数据到存储，并检查是否成功；创建或重命名文件后，要保证目录项持久化，还可能需要同步相关目录。端到端持久性仍依赖文件系统、设备正确遵守语义。

直接 I/O在适用条件下绕开文件页缓存数据路径，但有对齐和实现限制。它不自动等于同步写、不保证更快，也不是“完全不经过内核”。

很多连接，难道每个都派一个人盯着？

I/O 多路复用是用一次等待关注多个 fd 的状态。select、poll、Linux 的 epoll 都提供相关能力。epoll 让程序登记关注对象，再取得就绪事件，适合大量连接中只有部分活跃的场景。

例如服务有一万条连接，多数暂时没数据。线程等待事件集合，收到通知后处理有数据的连接，而不是不停轮询每个连接。收到可读事件后，仍要实际调用读取接口并处理竞争、断开、错误等情况。

这里主要讲 socket、管道等对象；普通磁盘文件并不能直接照搬 epoll 模型。epoll 不是所有操作都“严格 O(1)”，实际成本与活跃事件、注册操作及应用处理有关。

动手观察 · 教学模型

只读了一部分：LT 与 ET 有什么不同？

模型只有一个非阻塞 socket，每批数据仅在缓冲区为空时到达。先点“到达”，再通知、读 2 字节、再等待，比较两种模式。

把演示翻译成编程规则

LT（水平触发）：对象持续可读时，后续等待还可以报告可读。ET（边缘触发）：不能依赖“上次剩下没读完”在下一次等待时再次提醒你。

所以 ET 常与非阻塞 I/O 配合，每次收到可读通知后循环读取，直到 EAGAIN/EWOULDBLOCK，表示当前这轮已读尽。读取返回 0 通常是对端有序关闭，其他错误也要分别处理。

“ET 只通知一次”是不完整说法，不是连接一生只通知一次。以后出现新的相关事件仍可能通知；具体事件合并和再通知细节要遵守接口语义。上面的模型只用来理解为什么不能故意留着旧数据不读。

停一下，试着解释：epoll 返回可读事件，就表示数据已经复制到应用缓冲区了吗？

没有。它是就绪通知，应用仍要执行 read/recv 等读取操作。不能把多路复用直接称为所有读写都已完成的异步 I/O。

磁盘、分区、挂载与 LVM

从物理设备走到目录中的文件。

L21L34L35L36

文件夹怎样接到一块磁盘上？

磁盘是设备，分区是设备上划出的范围，文件系统是组织文件的规则，挂载是把文件系统接到目录树。这几个动作不能混成一个。

  1. 系统识别块设备，例如一块 SSD。
  2. 可以划分分区，也可以在适当场景下直接使用整块设备。
  3. 在设备或逻辑卷上建立文件系统，例如 ext4、XFS。
  4. 挂载到某个目录，例如 /data，之后从这里访问内容。

挂载不会把底层文件“移动”进目录。若挂载点原来有内容，它可能被新挂载遮住，而不是自动删除。df、findmnt 能帮助确认路径实际落在哪个文件系统。

块设备与字符设备

块设备支持按块组织的存储访问，适合文件系统，如磁盘。字符设备提供另一类设备接口，如终端、串口。名字中的“字符”不代表永远一次只能传一个字符，“块”也不代表应用只能发固定大小请求。

/dev 中很多条目是设备节点，供程序与驱动交互；驱动是内核中适配具体设备的代码。普通用户不需要自己知道每种硬盘的硬件命令。

LVM 为什么要再加一层？

LVM（逻辑卷管理）把“应用使用多大存储”和“底下是哪几块设备”分开。PV 是交给 LVM 管理的物理卷；多个 PV 组成 VG（卷组，类似空间池）；从 VG 分出 LV（逻辑卷），应用在 LV 上使用文件系统。

例子：VG 还有 50 GiB 空闲，想给日志用的 LV 扩 20 GiB。通常先扩 LV，再按文件系统支持的方式扩文件系统；只扩块设备层，文件系统不一定自动变大。

能否在线扩缩、怎样操作，取决于文件系统、卷类型及挂载状态。某些文件系统不支持缩小。LVM 不自动等于 RAID，也不自动等于备份；快照也不能代替独立故障域的备份。

机械硬盘为什么有“寻道”？

HDD 要移动磁头到目标位置，这叫寻道。教学里的SSTF（最短寻道时间优先）每次选择离当前磁头最近的请求，通常用磁道距离近似成本。

磁头从 50 出发，请求为 18、90、39、58、55。先去 55（5），再去 58（3），随后 39（19）、18（21）、90（72），总移动距离 5+3+19+21+72=120。每一步都从“新的当前位置”重新比较，不能只按离初始 50 的距离排序。

动手观察 · 教学模型

逐步选择离当前位置最近的请求

磁头 50；请求 18、90、39、58、55；不再加入新请求。教学用磁道距离，不把它当真实 SSD 时延。

别把教学模型硬套到所有设备

SSTF 不保证全局最优，也可能让远处请求长期等待。SCAN 类算法通过往返扫描减轻某些饥饿问题。SSD 没有机械磁头，现代设备还有内部并行、多队列等机制，所以实际 Linux I/O 调度不能只靠这个模型解释。

先用只读命令认清结构：lsblk -f 查看设备与文件系统，findmnt 查看挂载；有 LVM 时使用 pvs、vgs、lvs 查看各层。是否安装这些工具、权限是否足够因环境而异。格式化、改分区、缩卷会影响数据，本教程不安排在现有磁盘上试做。

停一下，试着解释：给 LV 加了空间，就可以断言 df 中立刻变大吗？

不能。LV 是块设备层，文件系统还需要按其支持的方式扩展；有的工具可组合执行，但仍是不同层的工作。

先看懂一条命令的结构

Shell 先解析你输入的文字，再执行命令。例如 ls -l /tmp：ls 是命令，-l 是选项，/tmp 是参数。命令可能是 Shell 内建功能，也可能是从 PATH 指定目录中找到的外部程序。

管道与重定向，就是在安排输入输出

grep、sed、awk 各擅长什么？

工具先学会的用途例子

sed对文本流做替换等编辑。sed 's/ERROR/WARN/g' app.log：输出替换后的文本，默认不改源文件。
awk按记录与字段处理文本。awk '{print $1, $3}' data.txt：默认按空白分字段，输出第 1、3 列。

正则表达式是一种描述文本模式的写法。^ 表示行开头，$ 表示行末，[0-9] 匹配一位数字；扩展正则中的 + 表示前一项出现一次或更多。grep -E 使用扩展正则。正则不是 Shell 的文件名通配符：*.log 在文件名展开和正则里的含义并不相同。

找最大的 5 个文件：先说明“大”的含义

这里比较文件逻辑字节数，不是实际占用磁盘块数；稀疏文件的二者可能不同。下面只读扫描当前目录的后代，不跟随文件符号链接，遇到不可访问项目跳过。真实大目录可能耗时，不代表这个简洁实现适合无限规模。

python
from pathlib import Path
import heapq

def candidates():
    for p in Path(".").rglob("*"):
        try:
            if p.is_symlink() or not p.is_file():
                continue
            yield p.stat().st_size, str(p)
        except OSError:
            continue

for size, path in heapq.nlargest(5, candidates()):
    print(size, repr(path))

stat().st_size 取逻辑大小；nlargest 保留最大的 5 个候选，不需要把所有候选排好序；repr 把文件名中的换行等字符显示为转义文字。目录遍历本身的权限行为依 Python 版本，脚本不是生产级审计工具。

本次已用 6 个临时文件实测：按大小得到 32、16、8、4、2；包含空格、换行文件名，并确认跳过文件符号链接。

从开机到服务可用

启动链路、systemd、发行版与定时任务。

按下开机键之后发生什么？

启动过程是逐层把更复杂的运行环境建立起来。常见 Linux 机器先运行固件（UEFI 或 BIOS），再加载引导程序或使用其他受支持的引导方式，然后启动内核。

  1. 固件初始化必要硬件，选择启动入口。
  2. 引导阶段加载内核以及可能使用的 initramfs。
  3. initramfs 是早期临时根文件系统，帮助准备驱动、解密或找到真正根文件系统；不是每种配置都必须用它。
  4. 内核建立基础环境，启动第一个用户空间进程。
  5. 在许多发行版中，PID 1 是 systemd，它按依赖启动服务、挂载等，逐步达到所需运行目标。

固件、内核、用户空间服务是不同阶段。云镜像、嵌入式系统、容器环境可能不同；容器一般不是完整重复宿主机固件到内核的启动链。

systemd：不只是帮你后台运行命令

systemd 是许多 Linux 系统使用的系统与服务管理器。unit 是它管理的单元，例如 service 表示服务，timer 表示定时器。它能组织依赖、启动、停止、重启策略和日志等。

systemctl start 是现在启动；enable 通常是建立随目标启动的关联，不等于立即启动；enable --now 才组合两者。daemon-reload 是重新读取 unit 配置，不等于重新启动应用。

为什么手动能跑，定时任务却失败？

cron 等定时执行环境通常没有你交互终端中的全部配置。常见差异包括 PATH、工作目录、账号权限、环境变量和 Shell。你的 alias、手动 export、当前所在目录，可能都不存在。

例如脚本里写 python app.py，定时运行时可能找不到 python，或者找不到相对路径 app.py。改为明确的解释器路径、脚本路径，必要时先进入工作目录，并记录标准输出与标准错误。

load average 与 CPU 使用率

Linux 的 load average 是一段时间内可运行任务与不可中断睡眠任务数量的平滑统计。三个数通常对应 1、5、15 分钟尺度，不是三个 CPU 的使用率，也不是 1 分钟窗口里的简单算术平均。

CPU 使用率问的是“采样期间 CPU 时间花在哪里”；load 问的是“有多少相关任务在运行、排队或特定等待”。二者不能互相替代。

例子：如果 4 个有效可用 CPU 上长期约有 8 个纯 CPU 可运行任务，可能存在排队。但容器配额、CPU 亲和性和 D 状态任务都会改变判断，不能一律把 load 除以物理核数当利用率。

案例 A：load 高，但 CPU 不高

  1. 先确认有效 CPU 额度与持续时间，排除刚发生的短峰值、配额限制或观察口径差异。
  2. 查看可运行任务和 D 状态任务。如果大量 D，考虑本地存储、网络文件系统等等待，但不要把所有阻塞任务都算入 load。
  3. 结合 iostat 的延迟与队列、vmstat 的换页活动、日志时间线，判断慢的是哪个资源。
  4. 定位受影响进程；有条件时再用 strace 等工具观察系统调用等待。跟踪会有开销与权限要求，先控制范围。
  5. 验证假设：例如存储延迟下降后，D 状态与业务延迟是否一同回落，而不是只凭一条命令宣布解决。

常见误区：普通可中断睡眠、等网络的连接、所有锁等待，并非都计入 Linux load 的不可中断等待部分。

案例 B：空间还有，为什么不能创建文件？

先区分报错是空间不足、inode 用尽、配额、权限还是只读文件系统。大量小文件可能耗尽 inode，即使还有可用数据块。inode 分配策略依文件系统而异，不是所有文件系统都具有相同固定上限。

先用 df -h 与 df -i 找对应挂载，再按目录缩小范围。对于“删除后空间没释放”，回到第 08 节检查仍被打开的已删除文件，别反复盲删目录。

资源限制：用户、进程、容器不是同一层

ulimit 是 Shell 提供的资源限制入口，例如 ulimit -n 查看打开文件数限制。软限制是当前约束，硬限制限制普通进程能把软限制调到多高；子进程通常继承限制。

Linux 的进程数量限制与真实用户身份等因素有关，可能按线程计数且对特权身份有例外；修改一个终端的 ulimit 不会自动改变所有既有服务。systemd 服务还有自己的配置，容器也可能另受限制。

cgroup 用于对一组进程做资源记账和限制，例如 CPU 额度、内存上限、任务数。namespace（命名空间）用于隔离看到的系统视图，例如 PID、挂载、网络。前者偏“能用多少”，后者偏“看到什么”；容器通常组合这些能力，并共享宿主内核。

限制能控制影响范围，但不是故障修复本身。fd 泄漏时只调大上限，往往只是延迟再次失败。

停一下，试着解释：CPU 不高，为什么机器仍然慢？

程序可能在等存储、网络或锁，也可能受内存换页、CPU 配额等限制。要把低 CPU 与任务状态、资源延迟和业务时间线联系起来。

把整条链路自己讲一次

假设你运行一个服务，它接收请求、读文件、更新计数器、写日志、最后退出。先不看答案，用下面六个问题检查理解。

停一下，试着解释：① 谁负责真正执行？谁安排轮到谁？

CPU 执行线程指令；内核调度器选择可运行任务。协程先由语言运行时安排到线程上，最终仍要线程获得 CPU。

停一下，试着解释：② 为什么程序不能随意读别人的内存？

每个进程有自己的地址空间，页表和硬件权限检查提供隔离，内核控制映射。受控共享是例外，不代表任意内存可访问。

停一下，试着解释：③ 等文件时，为什么其他请求还能处理？

等待中的线程可阻塞，CPU 让其他就绪线程运行；程序还可以用非阻塞 I/O 与事件通知组织大量等待任务。

停一下，试着解释：④ 两个请求同时给计数器加一，有什么风险？

读—改—写可能交错而丢失更新。需要保护整个临界操作，或使用语义合适的原子机制；加锁顺序还要避免死锁。

停一下，试着解释：⑤ 日志写成功，为什么还要讨论持久化？

成功可能只表示数据进入缓存。应用缓冲、内核页缓存、存储设备是不同层；需要根据可靠性要求使用正确同步协议，并检查错误。

停一下，试着解释：⑥ 删除日志和退出服务，会清理哪些东西？

删除名字减少链接；进程退出会释放它持有的 fd 等资源。还有其他名字或引用时对象仍可能存在。退出记录需要被父进程等回收。
